# MasterHUB display synchronization (offline)

`cooltek_sdk_service::display_sync` decides which key and dial images a MasterHUB display needs, and applies those decisions to a transport-agnostic sink. It is the offline half of live display support. Everything in it is tested with an in-memory fake. A HID-backed sink, a prepared key artwork provider and a generated dial artwork provider (function name, digital or analog clock, CPU usage, or the picture in the profile's `dial_display` setting) exist in the CLI crate and have offline fake-transport tests. The live runtime and `masterhub-service run` use them **only behind the experimental `--display-sync` opt-in**: M4315 keypad pages, or the M131E dial with `--dial-content`. The desktop app passes those flags to session-managed processes when Settings > Module control is **App** (the default); **Built-in animation** passes no display flags. See the [session manager](masterhub-session-manager.md#module-control). The M4315 keypad path has run on one real device (8 October 2026; see [Hardware results](#hardware-results-m4315-8-october-2026)). The dial path ran on one M131E on 8 October 2026 (the raw image upload and the four generated faces); see the [hardware results](masterhub-hardware-results.md#m131e-dial).

## Design

### Sink

`DisplaySink` is the boundary that hardware code implements (`HidDisplaySink`, below):

- `capabilities()` reports `key_count` (0 to 15 keys, wire indexes from 0) and whether a `dial` display exists.
- `write_key_image(key_index, jpeg, between_chunks)` writes one complete 72×72 key image.
- `write_dial_image(jpeg, between_chunks)` writes one complete 240×240 dial image.

`between_chunks` has the same shape as the hook of `dial::display_jpeg_with_pacing`, so a hardware sink can pass it straight through. Errors are `SinkError::Transport`, `SinkError::ShortWrite { written, expected }`, or `SinkError::Unsupported(target)`. A sink must stop at the first error or short write and must not retry, which is the SDK's existing policy.

`FakeDisplaySink` records every attempt (`writes`), returns queued faults per target (`fail_next`, or `fail_after` to let some attempts succeed first), and simulates `chunks` reports per image so pacing hooks can be checked.

### Artwork providers

The module renders nothing. It asks caller-owned providers for prepared bytes:

- `KeyImageProvider::key_image(&KeyImageRequest) -> Option<Vec<u8>>`. The request has the wire `key_index` and a `KeyContent`:
  - `Empty { page_id }`: an empty slot. Return a blank image so the previous page's artwork is cleared.
  - `Action { page_id, label }`: an action tile.
  - `Folder { page_id, target_page_id, target_name }`: a folder tile. Its label is the child page's name.
  - `Back { depth, parent_page_id }`: the generated Back key in slot 0 of every child page. The artwork is a left arrow with an `L{depth}` badge for the **current** depth (1 to 8), as described in [keypad folders](masterhub-keypad-folders.md). Drawing the badge is the provider's job.
- `DialImageProvider::dial_image(&DialImageRequest) -> Option<Vec<u8>>`. The request carries opaque `profile` and `function` strings. The caller maps its current profile and dial function onto them.

`None` means no artwork is available. The key or dial is reported as missing and is not written, so it may keep showing an older image.

### Planning

Planning goes through `DisplaySync::plan_page(&ProfileSession, &dyn KeyImageProvider)`. It is pure apart from reading the coordinator's drawn state. The underlying `DisplayPlan::for_page` and `DialPlan::new` are crate-private, so every plan is bound to the coordinator that made it. It takes the session's validated schema-2 profile and current path, requests all 15 keys in ascending wire order, and validates every returned image with `keypad::validate_jpeg` (72×72 baseline JFIF). It keeps only keys whose bytes differ from the last complete write. Diffing compares exact bytes, so unchanged artwork is never resent and edited artwork behind an unchanged request is still redrawn. One invalid image fails the whole plan before anything is written. Schema-1 profiles return `NotKeypadProfile`.

`DisplaySync::plan_dial(request, provider)` does the same for the dial with `dial::validate_jpeg` (240×240). The masterhub crate now exports that validator; before this change it was private.

`DrawnState` holds the last completely written bytes per key and for the dial. `None` means unknown or dirty. Callers can read it but not change it. It also holds the owning coordinator's ID, plus separate key and dial generation counters. A generation changes on every update to that surface's state: each successful write, each failure, and each invalidation.

### Applying

`DisplaySync<S: DisplaySink>` owns a sink and its `DrawnState`:

- `plan_page`, `apply(plan)`, and `sync_page` (plan, then apply) for keys. `apply_dial(plan)` for the dial.
- Before any write, `apply` returns `StalePlan` for a plan made by another `DisplaySync`, or for one whose key generation no longer matches. A generation mismatch means a later write, failure or invalidation happened after the plan was made. For example, a plan made before an apply that left key 4 half-written is rejected, so it cannot report success over a partial image. `apply_dial` does the same with the dial generation. `apply` also returns `Unsupported` for any key index the sink's capabilities do not cover.
- Writes are sequential in ascending wire order. A successful write records the bytes. A failed write sets that target to dirty, because the device may now hold a partial image. A fresh plan therefore rewrites it even when the bytes are unchanged. Plans made earlier are rejected, as above.
- `RetryPolicy { transport_retries }` defaults to 0, so at most `transport_retries + 1` attempts are made (256 at most). `WriteFailure::attempts` is a `u16`. Only `Transport` errors are retried. A short write is never retried. Retries run back to back, with no pacing or backoff between them.
- A `Transport` failure is recorded in `ApplyReport.failures` and the remaining writes continue. A `ShortWrite` stops the plan. Every key not yet attempted is listed in `not_attempted` and stays dirty.
- `with_chunk_pacing(hook)` is forwarded to the sink between reports of one image. `with_image_pacing(hook)` runs between consecutive key writes within one plan. It receives the number of keys already attempted, including failed ones. It does not run between retries or for `apply_dial`. Neither hook is set by default, and no delay value has been established.

### Invalidation and resume

- `sink_mut()` gives direct access to the sink, for example to inject faults into the fake. Writes made that way bypass validation and tracking, so handing out the sink invalidates all drawn state.
- `invalidate()`: forget everything drawn (after a reconnect, a profile replacement, or a focused-app switch). The next plans redraw every key and the dial, and older plans are rejected.
- `suspend()`: the same, because the device returns to hardware mode before sleep.
- `resume()`: invalidates and returns `ResumeAction { steps: [EnterSoftwareMode, QueryFirmware, RefreshDisplay] }`. This is the official app's sequence after its 2 s settle delay, from [static analysis](research/masterhub-1.0.0.113-static-analysis.md). The caller performs the device steps. This module sends no HID reports. For `RefreshDisplay`, call `sync_page` and plan the dial again.

## Hardware sink and artwork (implemented, wired behind an opt-in)

Automated tests for these pieces use fake transports. Manual runs of `masterhub-service run --display-sync` exercised the live integration on one M4315 and one M131E; see the hardware results below.

- **Typed short write (masterhub).** `dial::display_jpeg`, `dial::display_jpeg_with_pacing`, and the new keypad writers return a write count that differs from the report length as `HidError::IncompleteSendError { sent, all }`, HIDAPI's typed variant. `cooltek_sdk_masterhub::ShortWrite::from_error(&error)` returns `Some(ShortWrite { written, expected })` for it and `None` for every other error. Public signatures are unchanged (`HidResult<usize>`); only the error variant and its message changed. A count larger than the report is treated the same way.
- **Live key writer (masterhub).** `keypad::display_jpeg(transport, key_index, jpeg, output_report_length)` and `keypad::display_jpeg_with_pacing(..., between_chunks)` mirror the dial writer: they validate the key index, the complete image and the report length before the first write, write `keypad::JpegPackets` in order with `write_output`, run the hook between reports (n − 1 calls), and stop at the first error or short write without retrying or reading an acknowledgement. They send no mode command. Both writers share one internal report loop.
- **Shared transports (masterhub).** `ReportTransport` is now implemented for `&T`, `Rc<T>` and `Arc<T>`, so one opened device can back both an `InputReader` and a display sink.
- **`HidDisplaySink<T: ReportTransport>` (`crates/cooltek-sdk-cli/src/display_sink.rs`).** Implements `DisplaySink` for an M4315 (15 keys, no dial) or an M131E (dial, no keys). Construction reads the descriptor once and fails unless output report `0x02` has a length from 9 through 65,535 bytes. It never guesses a length. A typed short write becomes `SinkError::ShortWrite`, so `DisplaySync` never retries it. Every other error becomes `SinkError::Transport`. A target the module does not have is `SinkError::Unsupported`. `open_hardware(registry, identity)` opens a second handle and is not called: macOS opens HID devices exclusively by default, so a second handle is not expected to work there.
- **`SharedTransport<T>` (`display_sink.rs`).** `HidDevice` is `Send` but not `Sync`. The planned `Rc<HidDevice>` would keep display writes on the input thread, where input reads would wait for every key of a page. Instead, one opened device sits behind a mutex shared by the input reader and the display thread:
  - Reads take the lock in slices of at most 5 ms and return a normal timeout while another holder has it. Input reports queue in the OS meanwhile, so an in-flight display write can delay input reads.
  - A writer yields to a waiting reader after at most 16 output reports since the reader's last turn. Tests check this ordering by counting.
  - Feature reports and descriptor reads (mode commands) go before writers and wait at most 2 s, then fail with `SHARED_BUSY`.
  - `write_gate()`/`close_writes()` make every later output write fail immediately, checked before and after taking the lock.
  - A backend call that blocks inside HIDAPI is still not interruptible.
- **`PreparedKeyArtwork` (`crates/cooltek-sdk-cli/src/display_artwork.rs`).** A `KeyImageProvider`. Schema-2 tiles have no image field, so it serves deterministic generated placeholders: black for `Empty`, a solid slate tile for `Action` when no profile is given, a folder silhouette for `Folder`, and for `Back` a left arrow over an `L1` to `L8` badge drawn with a built-in 5×7 bitmap font (no font files). Each image is drawn into a 72×72 RGB buffer, encoded through `image_prep::prepare_keypad_image`, checked with `keypad::validate_jpeg`, and cached by `PreparedKeyArtwork::prepare()` before a run. Serving an image copies cached bytes. Nothing is encoded per input event. `Back` depths outside 1 to 8 return `None`.
- **Tiles without artwork (`tile_artwork.rs`).** `PreparedKeyArtwork::prepare_profile` draws every action tile that has no artwork of its own as an icon over its label (the tile's first binding picks the icon through `display_sync::TileIcon`, for example play, mute, volume, timer, screenshot, undo, OBS) in the same slate colour, using shapes and the 5×7 font. The label takes two lines of six characters at double size, else three lines of twelve at normal size, and is cut with a final dot when longer. The editor's preview draws an icon over the label too, so a profile made of labelled tiles (the built-in starters) shows pictures on the module. Drawn pictures were looked at on a rendered sheet; not yet seen on a module.

## Live integration (service flag; keypad run on one M4315, dial on one M131E)

`run_live_with_display` in `live_runtime.rs` takes an optional `LiveDisplay` (a boxed `DisplaySink` and `KeyImageProvider`, so tests inject `FakeDisplaySink`). It requires software mode, an M4315 session, and a schema-2 profile. The sink and provider move to a dedicated `masterhub-display` thread, which owns its `DisplaySync` and a copy of the profile session and applies the newest requested page path with `set_path`, then `sync_page`. The input owner stores a request in a single slot (newest wins) and never waits. Each outcome becomes a `display_sync` JSONL record that the action worker logs, and `service_end` gets display counters. The record and fields are documented in the [service guide](masterhub-service.md#keypad-display-sync-experimental).

The display runs on its own thread instead of the action worker, so display failures never dispatch, suppress, or reorder an action.

### Press feedback (`--press-feedback`, run on one M4315 with the service; see the hardware results)

With `--display-sync` on an M4315, `--press-feedback` draws a key dimmed (about 55% brightness) while it is held down. The input owner tracks the held key from each report's pressed and released events and puts it in the same single request slot as the page path (trigger `press`, or `navigation` when the press opens a folder, which then draws the new page with that key already dimmed). The display thread wraps the artwork provider for the held key only, so `DisplaySync` still diffs against what is drawn: a press costs one key write and a release one more, and a press that never changes a pixel (a blank black key) writes nothing. An animated key keeps animating while dimmed. Nothing waits for it: the action goes through the worker queue as before, and a press and release that arrive before the display thread wakes coalesce into no write at all. If a press-triggered sync takes longer than 150 ms, feedback is dropped for the rest of the run, since a late dim reads as lag. OpenStreamHub passes the flag when Settings > "Dim a key while it is pressed" is on (the default); the dial never gets it.

### Dial (run on one M131E)

`masterhub-service run --software-mode --display-sync --dial-content function|clock|analog-clock|cpu|image` on an M131E draws the dial screen. `--dial-content` defaults to `off`; any other value needs `--display-sync`, `--software-mode` and an M131E (checked before the device is opened, values parsed strictly). A flat profile is enough; no keypad tree is needed. What the OpenStreamHub app passes is each running profile's own `dial_display` setting (see [the profile's dial display setting](#the-profiles-dial-display-setting)); the standalone flag chooses by hand.

- **`DialArtwork` (`crates/cooltek-sdk-cli/src/dial_artwork.rs`)** is a `DialImageProvider`. It draws 240×240 RGB faces with a built-in rasteriser: a 5×7 bitmap font (A–Z, 0–9, common punctuation; anything else is `?`) and seven-segment clock digits, so no font file is read or downloaded. Each face is encoded through `image_prep::prepare_image` at quality 85 and checked with `dial::validate_jpeg`.
  - `function`: the active dial function's name (wrapped onto two lines of 11 characters, cut with `.` beyond 22), `n/N` above it and one dot per function below. Without `dial_functions` it shows the profile name. Every face is prepared before the device is opened.
  - `clock`: local `HH:MM` in seven-segment digits. `analog-clock`: a ring with hour ticks, an hour hand and a minute hand. Time comes from an injected `Clock` (`SystemClock` reads local time with `localtime_r`; tests use `ManualClock`). Off Unix, or if the conversion fails, the clock shows UTC. glibc's `localtime_r` does not re-read the time zone, so on Linux a time-zone change shows only after the service restarts; macOS re-checks it. A clock face is encoded when its minute is first requested and cached, so at most one image is encoded per minute. One clock face is encoded during preparation so a broken encoder fails before the run.
  - `cpu`: `CPU` above the whole-machine usage in seven-segment digits, `%` below, and a ring that fills clockwise from 12 o'clock (orange from 80 %). While no sample is available it shows a dim ring and `--`. A CPU face is encoded when its percentage is first requested and cached like a clock face; one face is encoded during preparation.
  - `image`: the exact picture stored in the profile's `dial_display` setting, served without drawing (validated twice: when the profile is stored, and again before a run starts). The profile may also keep the picture the image was made from (`dial_display.source`: a PNG or JPEG of at most 256 KiB, with its fit, quarter turns and background) so the app can re-fit it later; the dial never reads it and it is refused without an image. The image content ran on hardware on 11 October 2026 (see the hardware results).
  - Requests are opaque strings (`profile`, `function:<index>`, `clock:HH:MM`, `analog:HH:MM`, `cpu:<0-100>`, `cpu:--`, `image`, `image:<frame>` for an animated picture); a malformed or foreign request (for example `cpu:007`, `cpu:101`, or a CPU face asked of clock artwork) returns `None`. Equal requests mean the same face.
- **CPU usage.** `StatSource` is the sampler interface (`FakeStatSource` replays readings for tests). `cpu_usage::MacCpuStat` implements it with no new dependency: on macOS it calls `host_processor_info(PROCESSOR_CPU_LOAD_INFO)` through a minimal `extern "C"` block in `crates/cooltek-sdk-cli/src/cpu_usage.rs`; on other platforms it reports nothing. The one `unsafe` block lives in a single function: it passes live out-pointers, builds the slice from the element count the kernel returned (checked against cores × 4), copies the counters out, and always `vm_deallocate`s the array (and releases the host port) with no early return or panic in between. `CpuUsage` turns two samples into a percentage: per-counter `u32` deltas use wrapping subtraction, busy (user + system + nice) over all ticks summed over every core, rounded and clamped to 0–100. The first sample is a baseline (`None`). A read that worked but saw no elapsed ticks keeps the older baseline and repeats the last percentage, so an idle interval never shows `--` or reports the sensor as unavailable. A failed read or a changed core count restarts the baseline. `DialArtwork` samples only while building a request, at most once per `CPU_SAMPLE_INTERVAL` (1 s), so only the display thread samples, and only after its first request (sent once software mode is on); preparing the artwork samples nothing. The baseline is taken right after software mode is on, and the first face waits for the next sample (about a second), so a run does not start with a `--` write. A missing sample after that shows `--` and is reported once on stderr (a failed stderr write is ignored). A sampler that panics is treated as unavailable and never called again. Choosing the face (reading the clock, sampling the CPU) runs inside the display thread's panic guard, like the write: any other panic there is logged as a `display_sync` record with `trigger: "panic"`, `face: null` and the display-panic error, counts as a display failure, and disables the display for the run; input and the hardware-mode restore are unaffected. Right before it builds a request the dial thread checks the write gate and the interrupt flag, so no CPU sample starts once the gate has closed; one already running when it closes finishes before the thread exits, and the runtime waits for that exit before restoring hardware mode. GPU usage and temperatures need private IOKit or SMC interfaces and are out of scope.
- **Live path.** `LiveDisplay::dial` (built by `display_sink::live_dial_display`, which fails closed with `--display-sync setup failed` unless the sink has a dial) runs on the same `masterhub-display` thread design. The input owner requests a redraw right after software mode is enabled and after each report with a dial function switch, never waiting. The thread wakes for a request or every 100 ms, computes the face, and plans and applies it through `DisplaySync::plan_dial`/`apply_dial` only when the face changed (a new function, a new clock minute, or a new whole CPU percentage), at most once per `DIAL_MIN_INTERVAL` (1 s). A CPU redraw is logged with `trigger: "cpu"`. A newer request replaces an older one, so rapid clicks draw the newest function once the interval allows. Generation counters reject stale or foreign plans as for keys.
- **Animated picture.** A profile whose `dial_display` carries an `animation` (2 to 30 frames, each 150 ms to 60 s, at most 48 KiB a frame and 384 KiB together; the first frame equals `image`) plays it with `--dial-content image`. `DialArtwork::request` names the face `image:N` from the run clock (frame 0 is up at the first request, once software mode is on, so a slow device setup does not eat into a short or single-play animation), so the thread's ordinary "redraw when the face changed" rule draws each frame, at most once per `DIAL_ANIMATION_INTERVAL` (150 ms) instead of the one-second `DIAL_MIN_INTERVAL`. Dial writes log `elapsed_micros` (planning plus the write) when the dial was written. Clean animation frames are counted in `syncs` but only the first and then one in 50 are logged (`trigger: "animation"`), as the keypad's timed frames are not logged at all. A loop count of 0 repeats forever; a positive count is the number of plays, then the last frame stays. While an animation plays the thread sleeps until the next draw can happen (the rate limit opening, or the current frame ending) instead of waiting out its usual 100 ms tick, which keeps frames on time. A failed frame (transport failure or short write) holds the animation back for five seconds (or until the next request, such as a function switch), then tries the frame on the clock, so a failing dial logs about once in five seconds instead of five times a second and a transient fault does not stop the animation for the rest of the run. A turned module is handled once up front: the stored frames are rotated when the turn is set, not per frame. Measured on a real dial: a 44 KiB frame writes in about 100 ms (see the hardware results), so the 150 ms floor leaves a margin (a run at 150 ms: see the hardware results); the look is unchecked. The GIF is prepared from a canvas up to 512×512 (larger is refused), and when the frames together exceed 384 KiB the whole GIF is re-encoded at lower JPEG quality until they fit. A one-frame GIF is stored as a still picture. For comparison, the official app plays dial frames from a host loop at `max(delay, 66 ms)`, about three times faster than this floor, and always loops forever; the floor was lowered from 200 ms to 150 ms after the write time was measured, and going lower is untested (see [the source-map findings](research/masterhub-1.0.0.113-app-features.md#gif-playback-and-frame-timing-source-map-pass-19-october-2026)).
- **Failures.** A short dial write is never retried: `DisplaySync` does not retry it, and the thread does not try the same face again. A plain transport failure (for example `SHARED_BUSY` while the input reader holds the device) is retried once for the same face after the interval, so a function name does not stay stale until the next click; a second failure is left alone. Otherwise the next face change (function switch or minute) redraws. Each attempt is a `display_sync` record with `"target":"dial"`; see the [service guide](masterhub-service.md#dial-display-sync-experimental).
- **Safety.** The write gate, the bounded wait for the display thread, and the priority hardware-mode restore with its single busy retry are the same as for keys. Tests check that no dial write reaches the sink before software mode or after the restore (and, for `cpu`, that no CPU sample is taken outside that span either), that a stuck dial write yields to the restore, and that setup fails closed without touching the device. When the input loop ends, the runtime closes the write gate (a required `LiveDisplay::new` argument; `display_sink::live_display` builds the sink and passes the `SharedTransport`'s own gate, and the binary uses it), waits up to the cancellation budget for the display thread, and restores hardware mode with priority over display writes. If the lock is still busy, it retries the restore once. `service_end.display_stopped: false` signals that the display thread outlived cleanup behind the closed gate. Setup fails closed: a sink or display thread that cannot be created ends the run before software mode is entered. After that, a display failure is logged and never changes the exit status by itself.

## Modules turned on the base (`--display-turn`)

A module that sits turned on the base (its connector turns it a quarter, or the base itself is turned) shows what it draws sideways or upside down, because the screen belongs to the module. `--display-turn <0|90|180|270>` gives the module's turn clockwise from upright; the service then turns every key picture (72 x 72, each key on its own) and every dial face the other way before it is written, so the pictures read upright. Which key is which does not change: key indexes and input are the module's own, and a turned 15-key module simply has a 3 x 5 grid from the user's seat. The OpenStreamHub app passes the flag from the base's rotation plus the turn of the connector the module sits on (read from the slot table), or the rotation chosen for that module instead; the value is fixed when a run starts, so a change applies to the module's next run. Its preview draws the same upright pictures on the turned module.

Hardware (14 October 2026): the 15-key module on a connector that turns it 90 degrees clockwise, running with `--display-turn 90`, showed its key pictures upright. The dial and the other turns (180, 270) are not checked on a device; the direction is the same rule for all of them.

## The profile's dial display setting

A profile can add an optional `dial_display` object (`{"content": "off"|"function"|"clock"|"analog_clock"|"cpu"|"image"}`, with `"image": "<base64 JPEG>"` beside `image` content), which says what the M131E dial screen shows while that profile runs and the app drives the display. It is an additive optional field like `dial_functions`: old readers reject the file instead of silently ignoring it, existing files are unchanged, and there is no schema 3. Absent means the default: the active dial function's name, or the analog clock for a profile with nothing on the dial (no functions and no M131E binding), because there would be no name to show. The picture is a 240×240 baseline JFIF JPEG of at most 64 KiB (the app prepares uploads with the same pipeline as display artwork and lowers the quality until it fits); validation refuses anything else when the profile is stored. `image` content can also carry an `animation` (`{"frames":[{"jpeg_base64","delay_ms"}...],"loop_count"}`; limits under *Animated picture* above), whose first frame must equal `image` and which excludes a kept `source`; it is an additive optional field too. Only `image` content may carry a picture, and image content requires one.

Until 10 October 2026 the choice was one global setting in `display-settings.json` (earlier still, an experimental toggle); that field is ignored when an old settings file is read and is no longer written. The desktop app edits the setting in the dial inspector's Display tab, which previews the face with the same rasteriser the device gets; a running profile keeps the face it started with.

## Hardware results (M4315, 8 October 2026)

One M4315 on Apple Silicon macOS, connected directly to the Mac (behind the hub chain inside the MasterHUB unit). Profile: `examples/profiles/keypad-folders.json`. Command: `masterhub-service run --software-mode --display-sync --duration-secs N`, without `--execute`, so no action ran, except in the last row, which used `--execute`. The logs stay on the test machine. This is what they showed:

| Check | Result |
| --- | --- |
| Input without software mode | A passive 30 s capture recorded 0 reports. Keys report only after software mode. |
| Input in software mode | All 15 keys (indices 0 to 14) decode press and release correctly. |
| HID output report length | 320 bytes (ID 2), from the real report descriptor. The offline tests used a 65-byte stand-in. |
| First page | One `display_sync` record: `complete: true`, all 15 keys written, none failed or missing. The user saw the Mute tile on key 0, the folder tile on key 1 and 13 black keys. |
| Folder navigation | Three runs, 17 redraws in the longest. Root to Development to Git tools and back, four times. Every redraw was `complete: true` with no failure, drop or coalescing. |
| Diffing | Only changed keys were rewritten (for example `[0, 2]` from root to Development, because key 1 is a folder on both pages). |
| Press and release | A navigation press's release was logged `unbound`, as designed. |
| Real actions (`--execute`) | A scratch profile with `toggle_mute` on key 0 and `volume` +5 and -5 on keys 1 and 2: 9 of 9 presses logged `action_executed`, none failed. Four mute presses ended unmuted, and five volume presses (+5, -5, -5, +5, -5) changed 11% to 6%, as expected. Releases ran nothing. Shortcuts, app launch and the `obs_*` actions were not tested. |
| Session end | Clean `duration_elapsed` end with no error. The service restores hardware mode on exit, and each later run re-entered software mode normally. |

Still unknown after this session: the physical position of every key index (only keys 0 to 2 were seen to agree between input and display); redraw latency (logged, not timed); orientation and color accuracy beyond the first page. A later [app keypad dry-run](masterhub-hardware-results.md#desktop-app-keypad-dry-run-m4315-8-october-2026) verified two-level folder redraws, visible L1/L2 badges, reacting preview and normal Stop with the user. The dial results are recorded separately in the [hardware results](masterhub-hardware-results.md#m131e-dial).

The user confirmed the physical display looked correct, the preview needle reacted and stayed inside the screen, and normal Stop restored the built-in animation. See the [app dial dry-run](masterhub-hardware-results.md#desktop-app-dial-dry-run-m131e-8-october-2026) for the observed flags and counts. The M4315 App path was also verified with temporary unsaved two-level folders in Everyday: 16 events, no planned or executed actions, nine display-sync records, and user-confirmed redraws, L1/L2 badges, preview response and animation restore on Stop; see the [app keypad dry-run](masterhub-hardware-results.md#desktop-app-keypad-dry-run-m4315-8-october-2026). App-driven dial function cycling (Everyday has no `dial_functions`), changing Module control, normal Quit and other lifecycle gates remain untested. An earlier app dry-run software-mode dial session did exercise the stdin watchdog during an app crash; see [crash safety](masterhub-hardware-results.md#crash-safety-stdin-watchdog-m131e-dial-8-october-2026).
- **Dial faces.** On 8 October 2026 all four faces drew on a real M131E and were legible and upright (see the [hardware results](masterhub-hardware-results.md#m131e-dial)). Still unknown: whether the function label is clipped, whether the firmware tolerates the CPU face's once-a-second writes over a long run (only 25 s was tried), and clock minute rollover. Short-click function cycling was verified on 8 October 2026.
- **Dial framing and hardware limits.** On one M131E, a real 240×240 JPEG with header byte 6 zero displayed upright with the expected RGB colors. Two stress runs completed 21 uploads each, back to back and with a 50 ms gap, without errors; no acknowledgement or delay was needed in those runs. Flicker during transfer and rotations other than 0 remain untested; see the [hardware results](masterhub-hardware-results.md#m131e-dial). Offline framing tests separately use the 72×72 fixture and framing-valid variants of it, including a 240×240 header rewrite whose entropy data is not valid for that size. Those fixtures are not device captures.
- **Unknown timing.** Whether redrawing a full page is fast enough to feel responsive is unknown. The diff only reduces how many keys are written. On a shared device, an idle input reader holds the lock for read slices of up to 5 ms with gaps of about 1 ms, and a writer sends at most 16 reports per gap. A page redraw may therefore be noticeably slow. The 8 October run logged redraws but did not time them; measure them.
- **Image cut short at session end.** When the write gate closes mid-image, that key's JPEG transfer is left incomplete just before the hardware-mode restore. How the firmware handles a partial image followed by a mode change is unknown and hardware-unverified.
- **Panics.** A panic inside the input loop is contained. The run then ends with `input loop panicked`, and cleanup, including the hardware-mode restore, still runs. A panic later on the coordinator thread (display stop, drain, worker completion) is contained too: the display gate is closed, the worker is cancelled, the restore still runs with its single busy retry, and the run fails with `live session coordinator panicked` plus the panic message. That late path writes no `service_end` footer.

## Integration checklist for the live run path

1. **Hardware sink (masterhub crate and CLI). Done, offline only.** See above: typed short write, `keypad::display_jpeg_with_pacing`, `HidDisplaySink`. Tested with fake transports for exact report bytes, stop on short write, pacing counts, nothing written for an invalid image, `ShortWrite` never retried by `DisplaySync` (even with `RetryPolicy { transport_retries: 3 }`), the chunk pacing hook reaching the HID writer, and unsupported targets.
2. **Software mode. Done, offline only.** `live_runtime.rs` enters keypad software mode when `LiveOptions::software_mode` is set (`crate::mode::set`, after the worker reports ready). The sink sends no mode command. A display requires software mode: the CLI rejects `--display-sync` without `--software-mode` before HID access, and the runtime rejects it again before starting the worker.
3. **Lift the rejection. Done behind an opt-in.** `live_bindings` keeps the schema-2 keypad tree for an M4315 only when `--display-sync` is given, and rejects the flag for any other module. Without the flag it returns "nested keypad profiles run live only with --display-sync (which requires --software-mode); in OpenStreamHub, set Module control to App in Settings" (`service_events::NESTED_KEYPAD_REFUSAL`). The flag stays opt-in for the standalone service; the desktop app passes it by default (Module control App) and shows its own message, naming the setting, instead of this one.
4. **Initial draw and navigation. Done, offline only, with one deliberate change.** The planned `Rc<HidDevice>` sharing would keep display writes on the input thread, so the sink is shared through `SharedTransport` and runs on a dedicated display thread instead (see above).
   1. Caller (`masterhub-service.rs`): `PreparedKeyArtwork::prepare()` runs before HID access. The device is opened once and wrapped in `SharedTransport`. `HidDisplaySink::new` gets a clone (via `display_sink::live_display`) and `InputReader` takes the original. A failed sink construction is a setup error before software mode (fail closed). Tests never construct this path.
   2. Right after `crate::mode::set(…, true)` succeeds, the first page is requested (`trigger: "software_mode"`).
   3. After each report, once its work was offered to the worker or coalesced, a page is requested if any of its events is a keypad `Navigation`. The display thread keeps one pending request, and newer pages replace older ones.
   4. Each `ApplyReport` and the plan's `missing()` are logged as a bounded `display_sync` record. `service_end` adds `display_sync_count` and `display_failure_count`, plus coalesced-request, dropped-record, and `display_stopped` fields.
   5. A `DisplayError`, failed write, or stalled sink is logged and ignored. It never returns an error from the loop, dispatches or suppresses an action, or changes the exit status by itself. An in-flight write can delay input reads (see `SharedTransport`). No sync starts after the input loop ends or the interrupt flag is set, and the closed write gate makes an in-flight sync fail its remaining keys at once. Hardware mode is restored with priority and retried once on a busy lock. A short write leaves keys dirty, and the next navigation redraws them.
5. **Artwork provider. Done, offline only.** `PreparedKeyArtwork` (above). Real tile artwork needs an image field in the profile format first, which does not exist.
6. **Dial. Done; run on one M131E.** `DialArtwork` maps the profile and the current dial function index (or the clock's minute, or the CPU percentage) to a `DialImageRequest`, and the dial display thread calls `plan_dial` and `apply_dial` when the face changes, at most once a second, or every 150 ms for an animated picture (see [Dial](#dial-run-on-one-m131e)). Behind `--display-sync --dial-content`.
7. **Reconnect and profile switch. Nothing to wire today.** The live runtime has no reconnect, software-mode re-entry, or in-process profile replacement path. A read error ends the session, and the desktop app restarts the process for wake and for a focused-app profile switch. Each process creates a new `DisplaySync`, which starts dirty and redraws all 15 keys on its first sync. If such a path is ever added, call `invalidate()` there and then request a sync.
8. **Tauri session manager resume. No change needed today.** `apps/open-stream-hub/src-tauri/src/session.rs` stops the service on suspend and restarts it after wake (`Event::Resume`, 2 s settle). A restarted service process creates a new `DisplaySync`, which starts dirty and redraws everything on its first `sync_page` (or its first dial face). With Module control App, the restart passes the display flags for the session's settings and the profile it now runs. A resume hook is needed only if the service is ever kept alive across sleep. In that case call `suspend()` on sleep and `resume()` after the settle delay, then perform its steps in order: software mode, firmware query (`dial::read_firmware_info` for the M131E), then `sync_page` and dial planning.
9. **Hardware session. Partly done.** On 8 October 2026 the keypad ran on one M4315 and the dial faces on one M131E (above and in the [hardware results](masterhub-hardware-results.md)), and the desktop app now passes the flags by default (Module control App). Still to verify: the physical position of keys beyond 0 to 2, orientation beyond the first page, pacing under load, the behaviour after a short write, and page-transition latency (logged, not timed). Record results in the [hardware results](masterhub-hardware-results.md).
