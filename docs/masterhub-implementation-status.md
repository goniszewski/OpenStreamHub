# MasterHUB implementation status

Updated on 7 October 2026. The SDK implements discovery, input decoding for all five control modules, IPS mode controls, dial JPEG output, offline per-key JPEG packets, and dial session lifecycle hooks. The CLI prepares static images for both IPS modules offline. A separate binding service adds profiles and explicit macOS actions. The [OpenStreamHub desktop app](../apps/open-stream-hub/README.md) provides profile editing, device-free replay, a live module preview, supervised action runs with sleep/wake and reconnect handling, and offline artwork preparation. Automated tests use synthetic reports, simulated transports, and mock host processes; limited device-free macOS checks are recorded in the [smoke guide](masterhub-macos-smoke.md). Hardware compatibility and complete action acceptance remain pending. See the [roadmap](masterhub-macos-plan.md), [diagnostic guide](masterhub-diagnostics.md), [service guide](masterhub-service.md), [session manager](masterhub-session-manager.md), and [Windows parity tracker](windows-parity-gaps.md).

## Implemented

- Shared HID discovery with lossless paths and interface/usage metadata. Exact identity opening verifies the selected enumeration snapshot and the opened handle before initialization is available.
- Module PID aliases: base `01f6`/`9999`, knobs `0202`/`9996`, dial `0206`/`9994`, keys `01fe`/`9997`, faders `0200`/`9991`, and rollers `0204`/`9995`, with vendor `2516`. Discovery and typed handle matching accept both generations. Original `PRODUCT_ID` constants remain unchanged; custom modules can override `Module::accepts_product_id`.
- Separate neutral opening and explicit initialization on typed module handles. The serial example no longer initializes the IPS dial as a side effect.
- Fakeable report transport and bounded input reader; actual received lengths are respected, idle timeouts and transport errors are distinct, and input reading performs no feature queries/configuration writes.
- Safe serial response parsing with actual-length, header, report-ID, and payload bounds validation. Existing lossy UTF-8/NUL-padding behavior is preserved.
- Pure M0 framing and M003K logical parsing with typed rotation and press/release transitions. Malformed reports never partially change state; unknown channels/report IDs retain original bytes.
- M4315 press/release decoding for all 15 keys, M005S absolute position decoding for all five faders (0–100), and M032LE discrete Up/Down updates for both rollers. Complete snapshots validate before state changes; faders emit initial positions and subsequent changes, keys deduplicate transitions, and repeated roller directions remain events. Physical placement/direction remains unverified; see [additional-module evidence](research/masterhub-additional-modules-1.0.0.113.md).
- Explicit M4315 software-mode feature reports (`03 3a <bool>`, 32 bytes); recording and live service accept the opt-in flag for keys as well as the dial, with one-shot mode restoration after enable attempts.
- Bounded M131E framing and a stateful dial decoder. Queue 0 produces application RIGHT/LEFT rotation labels and press/release transitions; physical clockwise/counterclockwise mapping remains unknown. Ignored payload byte 1 and extra bytes are retained. Other queues, unsupported selectors, and unknown layouts retain the original raw report.
- Dial feature builders and explicit transport/typed-handle methods for software/hardware mode, backlight, solid color channels, backlight queries, and firmware information selectors. Replies are bounded by the actual returned count. Reply byte 1 and firmware bytes retain unresolved semantics; no Windows returned-count increment is copied. The color channel order (R, G, B) was verified on one M131E; see [hardware results](masterhub-hardware-results.md).
- Pure HID descriptor inspection and descriptor-sized JPEG output. The packet iterator accepts an encoded 240×240, 8-bit, three-component baseline JFIF JPEG with one interleaved scan; it checks markers/dimensions but does not decode entropy data. Chunk sequence/length fields and final flags follow the recovered SDK layout. Header byte 6 and unused padding are zeroed deliberately. Typed display upload queries the selected interface's descriptor and fails if its output size cannot be established; short writes stop without retry or inferred acknowledgement.
- Pure M4315 per-key `JpegPackets` and `validate_jpeg()`, using conservative 72×72 baseline JFIF input. The header carries `02 36`, 16-bit sequence/length, key index 0–14, and final flag; report lengths come from a supplied descriptor. Image/report/key bounds and at most 65,536 chunks prevent overflow; each report has fresh zero padding. `JpegPackets` performs no I/O. The live key writer (`keypad::display_jpeg`) is used only by the experimental `masterhub-service --display-sync`, never run on hardware; the CLI has no live key upload.
- Explicit `DialSession` activation, suspension, caller-timed resume, input reads, and shutdown. Construction/drop perform no commands; firmware queries and display refresh remain explicit caller operations. The two-second resume delay is application-derived policy. `DialGestureTracker` optionally classifies a known press/release at the app's 600 ms threshold using caller-provided monotonic timestamps; it does not invent a firmware long-press event.
- `masterhub-diag list`, `record`, and `replay`. Recording has a finite deadline, exact-path selection, no-overwrite output, descriptor result, provenance, and error footer. Software mode is an explicit option for M131E or M4315.
- Strict, versioned JSONL replay with bounded records, count/timestamp/footer checks, original raw reports, explicit packet parse errors, and final capture status. Replay never opens hardware or dispatches actions.

## CLI replay and display controls

- Replay selects the decoder for any of the five control modules using actual VID/PID, including legacy and newer aliases, rather than a potentially incorrect model label. Dial output preserves raw bytes and includes optional host gestures at the 600 ms boundary.
- `dial mode`, `dial backlight`, and `dial color` preview complete feature reports by default. Only an explicit `--path-hex` opens and writes to an exact selected dial. All dial commands check the vendor/product IDs and reject keypads and other module paths before opening them. `dial info` explicitly queries firmware fields and backlight.
- `dial jpeg` plans packets offline from a saved HID descriptor and encoded JPEG, or explicitly writes to a selected dial using its descriptor. The JSONL plan has separate provenance/schema from input captures. Inputs are validated before plan creation or the first display write; existing output files are never overwritten.
- `dial prepare-image` decodes static PNG/JPEG, fits and optionally rotates/mattes the image, and encodes 240×240 RGB baseline JFIF. Source bytes, dimensions, and decoded pixel buffers are bounded; APNG and unsupported formats are rejected. EXIF orientation and color profiles are not automatically applied. Full conversion and framing validation precede no-overwrite file creation; no HID context is constructed.
- `keypad prepare-image` uses the same bounded static-image conversion with a 72×72 target. `keypad jpeg` plans one key image offline using required `--key-index`, `--descriptor`, and `--output`; its JSONL metadata identifies M4315 and the key. Validation precedes no-overwrite creation. There is no live path or HID context.
- Opt-in recording attempts hardware-mode restoration after success, read failure, or even a failed initial software-mode write. Primary capture/enable errors, footer failures, and cleanup failures remain visible. The input footer alone does not establish successful cleanup.
- Help, examples, fixture provenance, and command constraints are documented in [masterhub-diagnostics.md](masterhub-diagnostics.md). Offline paths do not enumerate or open hardware.

## Binding and action service

- Separate `cooltek-sdk-service` crate with strict schema-1/schema-2 profiles, bounded action validation, serial-specific precedence, input normalization, and the host dispatcher boundary.
- Stateful `ProfileSession` routes schema-2 keypad events through the current page and retains press origins for release actions. CLI replay logs folder navigation without dispatching an action. Live schema-2 keypad runs are rejected before opening HID unless the experimental, hardware-unverified `--display-sync` opt-in is given; schema-1 keypad and non-key module runs retain their existing behavior. `--display-sync --dial-content function|clock|analog-clock|cpu` draws generated M131E dial faces at most once a second ([display sync](masterhub-display-sync.md)); `cpu` reads whole-machine CPU usage through the Mach `host_processor_info` call on macOS (no new dependency; `--` elsewhere; no GPU or temperature data).
- `masterhub-service validate`, `replay`, and `run`. Replay constructs no HID context and always plans actions. Live runs own one exact selected interface, log planned actions by default, and require `--execute` for host operations. IPS module software mode is a separate explicit option.
- A `profile` action (next/previous saved profile, as the official app's `profile` key) is never executed on the host. With `--profile-switch-requests` the service logs `profile_switch_requested` for the desktop app's session manager; without it the action is logged as `action_unavailable` and the run continues. See [actions](masterhub-actions.md#profile-nextprevious-profile).
- A `timer` action (as the official app's `timer` key: a 1 s–24 h countdown with an end sound) is owned by the service worker: a press starts it, a second press of the same binding cancels it, at most 8 run per process, and all are cancelled when the run ends (including the session manager's stop before sleep). At expiry the macOS backend posts a notification (fixed AppleScript, label as an argv item) and plays a fixed system sound (3 s and 6 s bounds) on a per-session alert thread, so a playing sound never delays actions; a stop kills a running alert. Records never contain the label; a notification refused with a stderr message is logged as `timer_alert_warning`. Unlike the official app, the countdown is not drawn on the key. Notification delivery and sound playback are unverified on a real Mac. See [actions](masterhub-actions.md#countdown-timer-timer).
- `media` executes on macOS: `play_pause`, `next_track` and `previous_track` post a hardware media key (key-down then key-up `NX_SYSDEFINED` events) through `/usr/bin/osascript -l JavaScript` with a fixed script whose only input is a key type from a closed set; the script checks the post-event (Accessibility) permission first and reads the events back before posting. Only a run's first media key may show the Accessibility prompt. `stop` has no media key, so it stops Apple Music (a pid-addressed Apple event) and pauses Spotify, each only if already running, re-checked just before the command; it does not start a player that is not running, but macOS may relaunch Spotify if it quits in that instant (without playing); with neither running it does nothing. Tested with a mock process host and by compiling the scripts with `osacompile`; never run against a real player. See [actions](masterhub-actions.md#media-control-media).
- `obs_scene` switches the OBS program scene over obs-websocket v5 on a loopback endpoint (`--obs-endpoint`, never from a profile), one bounded connection per action with a hand-written, strictly bounded WebSocket client; the OBS password arrives on stdin only (`--obs-password-stdin`). Without an endpoint the action is logged as `action_unavailable`. Tested against fake loopback servers only; never run against real OBS. See [actions](masterhub-actions.md#obs-scene-obs_scene).
- macOS system output volume/mute, ASCII keyboard shortcuts through System Events, and application launch by bundle ID. The backend uses absolute system binaries with argument validation, five-second subprocess timeouts, bounded output, and no retries.
- Public `AudioSnapshot`, `audio_snapshot()`, and `restore_audio_snapshot()` helpers support bounded state queries and exact best-effort restoration. Device-free smoke examples verify audio effects and restoration, or request a TextEdit launch/plain scratch keystroke; explicit execution is required. Native command completion is distinguished from independently observed effects.
- Live input is timestamped and normalized independently of the action worker. Owned reports enter a 64-report FIFO queue; overflow ends the session with explicit received/queued/processed/discarded counts. Actions remain ordered and serialized.
- Live logging uses a 500 ms total record deadline and bounded records on terminals, pipes, or sockets. A failed/partial record cannot be retried; regular-file redirection is rejected and an active `tee` pipeline can save output. The owned stdout duplicate restores status flags when dropped.
- Normal input limits allow a ten-second worker drain, followed by cancellation when necessary. Ctrl-C/SIGTERM and failures cancel queued work and in-flight native subprocesses; completion is observed before joining. Requested IPS module hardware-mode cleanup runs once after the finite worker phase and any software-mode attempt, including failed enabling. Primary, action, drain, output, and cleanup errors are preserved in the final status.
- Diagnostic path parsing now treats a lossless path as one required value, avoiding a Clap type mismatch on valid live arguments. Existing diagnostic commands remain the Cargo default binary.
- Tests cover input continuing during blocked actions, both gesture thresholds, rapid ordered bursts, queue overflow, blocked pipes, subprocess cancellation, failed-action stopping, and uncooperative-worker deadlines. Host arrival timestamps and queues do not establish device timing, sustained hardware throughput, or absence of HID buffering loss. HIDAPI feature cleanup is synchronous without an exposed timeout. The service itself has no reconnect or sleep/wake logic; the desktop app supervises it instead (see Desktop app). Neither has been exercised on hardware.

## Desktop app

- OpenStreamHub uses Tauri 2 and React/TypeScript under `apps/open-stream-hub`, with separate dependency lockfiles and Rust workspace. The macOS application bundle requires macOS 12.3 or later, includes its frontend and runs without a development server.
- All five module types in the catalog, with fixed image columns and system/light/dark appearance. Clickable artwork and a keyboard-accessible picker select the same per-control binding editor; the fader preview carries its absolute position into the service resolver.
- Create, edit, validate, save and reload service profiles. The native backend bounds reads, validates UUID storage identifiers, rejects symlinks, preserves invalid files and replaces saved profiles atomically. Saving is automatic by default: an edit is written shortly after it settles, and each overwrite keeps the previous version (newest 20 per profile in a hidden `.history` folder) for the profile manager's Earlier versions list. Switching, reloading, closing the window and starting a run settle the pending edit first; the unsaved-changes guards remain for when a change cannot be saved (the setting off, a new profile, or a name still being retyped), and a save that hits a file changed on disk elsewhere refuses and stops until reload.
- First launch under the OpenStreamHub identity validates and copies the previous desktop app's profiles when the new store is absent. UUIDs, JSON contents and modification times are preserved; originals and existing destination stores are never overwritten. Appearance falls back to the previous key only when that webview storage is accessible.
- Selected-event previews and five bundled synthetic captures use the shared capture reader, decoder, binding engine and `DryRunDispatcher`. Results include planned/unbound actions and malformed/unknown-report diagnostics. The desktop bridge exposes no HID or host action execution command.
- Nested keypad folders with 15 root slots, 14 child slots and a generated Back key showing the current L1–L8 depth. Breadcrumbs, folder naming, subtree deletion confirmation, per-page action editing and complete-click simulation share the validated schema-2 layout. Schema-1 files upgrade in memory and change on disk only after explicit Save. See [folder design and acceptance](masterhub-keypad-folders.md).
- Undo/redo, binding search and conflict warnings in the editor; profile duplicate, import and export; crash-safe drafts; connection notices. The first launch on a fresh, empty profile store offers three shipped starter profiles (Mac basics, Streaming (OBS), Editing and media — volume, playback, screenshot, timer and name-free OBS actions only, so nothing is typed into apps and no program or web page is opened); picking one creates a new saved profile. Starters that use a module are offered again when that module is connected after launch, and the profile manager's New from a starter opens the same chooser; the getting-started guide is reachable from Help and Settings.
- Official `.mhz` profile import (`src-tauri/src/mhz/`): an in-memory, bounded ZIP and JSON read with no extraction and no shell, mapped by the table in the [`.mhz` format analysis](research/masterhub-mhz-format.md). Each profile becomes a new, dry-run-only profile with a redacted per-control report; provenance follows content hashes and source ids, so copies, edits and re-imported exports stay dry run only; unsupported and dangerous actions (programs, macros, scripts, integrations, images) stay unbound. The session manager refuses Execute for it until the user allows actions ([session manager](masterhub-session-manager.md#imported-profiles-dry-run-only), [user guide](importing-masterhub-profiles.md)). Tested with synthetic files only; `.mhz` export is not implemented. A live rig preview shows the modules and hot-plug detection updates the inventory.
- Offline display artwork preparation reuses the CLI conversion; the workspace's key artwork editor composes an icon (bundled library, action suggestions, an installed app's own icon) and label text on a canvas and prepares the same 72×72 JPEG the key receives. The studio design is stored as optional metadata on the prepared artwork (`KeyArtwork.design`), so reopening a key restores the icon, text and colours; an unresolvable icon id falls back to the default suggestion, and applying an uploaded image clears the design. Settings > Module control is App by default: session-managed runs on the M4315 and M131E request software mode and pass `--display-sync` (and `--dial-content`), read once per Start; Built-in animation leaves both modules in their own mode ([session manager](masterhub-session-manager.md#module-control)). Run on one M4315 and one M131E ([hardware results](masterhub-hardware-results.md)).
- A Lighting page applies the encoder dial's backlight (0–100) and one solid colour live through the app's own HID handle (`set_dial_lighting`/`reset_dial_lighting`): an apply puts the dial in software mode first, then writes the backlight and the colour — the sequence verified on hardware — and Reset leaves software mode so the built-in animation returns. Whole kit reaches every connected dial; a dial a running profile owns refuses the write (the same rule as feeds), and unsupported modules show disabled controls with the reason instead of hiding them. Targets are re-checked for the module kind on every write. Knob rings, base edge and fader lighting wait for their protocol. The page's own hardware check is recorded in [hardware results](masterhub-hardware-results.md).
- Supervised runs: the app starts `masterhub-service` as a bundled Tauri sidecar (or via `OPEN_STREAM_HUB_SERVICE`) inside a session. User-started Execute sessions need explicit confirmation again after an interruption. App-started sessions are dry runs by default; the separate, off-by-default “Run actions automatically” setting allows them to execute and restart automatically after sleep, reconnects, crashes, or profile changes, subject to a fresh execution-guard check. A global default profile can be selected for automatic starts, with per-module last-used and blank-profile fallbacks. A profile key (next/previous) switches a managed run to another saved profile in name order through the same path as focused-app rules: debounced and ignored while asleep or with a single saved profile. See the [session manager](masterhub-session-manager.md) and [building the desktop app](building-the-desktop-app.md). The new automatic execution and default-profile flows have automated tests but have not been tested on hardware.
- Settings > OBS Studio: an off-by-default loopback OBS endpoint stored in `obs-settings.json` and a password kept in memory only (entered per app launch), snapshotted at each Start like the display setting and passed to the service as `--obs-endpoint` plus a stdin pipe ([session manager](masterhub-session-manager.md#obs-websocket)).
- A local diagnostic bundle collects hardware and app details for the first hardware session; nothing is uploaded. With serial redaction on, text snippets, URLs, timer labels and OBS scene names in the embedded profile and activity are redacted, and the OBS password is never included. See the [diagnostic bundle](masterhub-diagnostic-bundle.md).
- Browser preview is read-only. Focused-app routing, browser adapters, verified display uploads, flows and user scripts remain planned; see [focused-app rules](masterhub-focus-rules.md).

## Remaining gates

The first hardware session must establish descriptors/topology, interface selection, actual serial/report framing, physical control order and gestures, required initialization, and native HID timeout/open behavior. Complete dial payloads, descriptor sizes, physical direction, color order, feature-field semantics, image acceptance/orientation, header byte 6, and pacing still require captures or device tests. Implemented aliases, decoders, commands, and packet construction are not hardware acceptance.

Wider hardware acceptance of the experimental key display sync (one M4315 session is recorded in [display sync](masterhub-display-sync.md#hardware-results-m4315-8-october-2026)), hardware acceptance of the dial display sync, base/knob lighting, complete action/permission runtime acceptance, hardware acceptance of the desktop app's live preview, sleep/wake and reconnect behavior, signed/notarized release packaging (see the [release process](release-process.md)), and firmware compatibility acceptance remain later roadmap milestones. SDK lifecycle hooks do not recover devices by themselves; automatic recovery exists only in the desktop session manager and is untested on hardware. Static PNG/JPEG conversion is implemented; BMP, animation, and progressive JPEG output remain unsupported. Firmware flashing/recovery remains excluded.
