# OpenStreamHub service session manager

The desktop app (`apps/open-stream-hub`) wraps every `masterhub-service run` that it starts in a **session**. A session keeps the run alive across system sleep, unplugging, and service crashes. The service has no reconnect logic of its own; see [masterhub-service](masterhub-service.md). The code is in `src-tauri/src/session.rs` (state machine and driver) and `src-tauri/src/power.rs` (sleep/wake events). None of it has been tested on hardware. The tests use a fake clock, a fake service runner, a fake inventory, and fake power events.

## Identity and ids

- A session stores the original `start_service` request: profile snapshot, `execute`, and `software_mode`. Every restart reuses that request and changes only `path_hex`.
- The device is identified by **module + serial number**. HID paths can change after a replug or wake, so the session never relies on the path alone. To find a device again, the session needs an exact serial match. For a device whose serial is null or blank, it accepts a candidate only if exactly one device of that module is present. If several are present, the session keeps waiting with the detail `ambiguous device`. A different serial on the same port never counts as the same device.
- The session id is the first process's service id (`service:<path_hex>`) and does not change while the session lasts. When that id still names an older session that moved to another path, the new session is named `session:<uuid>` instead. `service_id` in the state event names the current process, which may have a different id after a replug, or is `null` when no process is running. `service://status` and `service://record` keep using the current process's id.
- `start_service` returns the **session id** for a managed run (including a start while asleep and a `session:<uuid>` name), or the service id of an unmanaged run. The frontend keys the run by that id as soon as the command resolves. Before that, a run that waits under its own key (`pending:service:<path>`, because a live session still carries that name) is matched to its first state event by the event's `service_id`, or, when the event has no process yet (a start while asleep), by the module and serial number the run was started on. The `start_service` reply can arrive before Tauri events that were sent earlier. If the reply names the path's own service id while the older run of that name has not yet reported `stopped`, the waiting run keeps its `pending:` key. The old session's remaining events, including its `stopped`, still update the old run, but none of them takes the path's `service://status` and `service://record` routing from the waiting run. The new process's status (`starting`, then `running`, which the backend reports inside `start_service`, before the session's first state event) and records therefore land in the waiting run. A waiting run stays eligible while its process has not ended (`starting`, `running`, or `stopping`). The new session's first event that is not `stopped` then adopts the waiting run, keeping its profile, profile generation, log, and counters, and replaces the old run. The same happens when that first event arrives before the reply: it is matched to the waiting run by its process id, or by module and serial number when it has no process. The old run never receives the new session or its process's status, the adopted run never takes the old run's profile or generation (so its Resume names the generation the new session reports), and a late `stopped` from the old session never ends the adopted run. The waiting run therefore leaves its `pending:` key once its session reports, and does not block later starts or stops on that path.
- Each session runs at most one process at a time. Two sessions can never share a device identity: `start_service` refuses a device that another session already owns. A serial-less device has no identity to compare, so a session without a process that waits for the same module, also without a serial (for example one started while asleep), claims every serial-less device of that module on any path, exactly as its reconnect picks the only device of that module. A second start is refused. A stopped session, or one whose process is still stopping, claims nothing.
- Every start runs the same request checks before a session exists, whether or not it spawns now: a valid profile, an execute mode the platform supports, and no process already running on that path (`Runner::check`, which uses `service::check_request`). An invalid profile started while asleep is therefore refused at once, not after wake.
- When the app cannot identify the device from the latest inventory or from a fresh enumeration, it starts the service **unmanaged**, as it did before sessions existed. No session events are sent for that run.
- The app falls back to unmanaged runs only when no session driver was started. If the driver thread has died, `start_service` is refused with `session::DRIVER_STOPPED`, because an unmanaged run would ignore sleep. `stop_service` still stops the plain process in that case, since stopping never spawns anything. `stop_session` has no plain process to fall back to, so it returns `DRIVER_STOPPED` instead of silently doing nothing.

## Phases

| Phase | Meaning |
| --- | --- |
| `running` | The service process is running. |
| `suspended` | The system is asleep, or the 2 s settle delay after wake has not ended yet (`next_attempt_in_ms` shows the remaining time). |
| `waiting_for_device` | The device identity is not in the inventory, or the match is ambiguous. |
| `reconnecting` | A restart is in progress or scheduled (crash backoff, shown in `next_attempt_in_ms`). |
| `needs_confirmation` | The device is back, but the session executes actions, so it waits for the user. |
| `stopped` | Final. `reason` is `user` (stop or app exit) or `service_exited` (too many crashes). |

`reason` gives the most recent interruption: `sleep`, `device_removed`, `service_exited`, `user`, or `profile_switch` (a [focused-app rule](masterhub-focus-rules.md) replaced the profile). It is `null` while the session is `running`. `detail` holds the last nonblank stderr line of a crashed service (at most 512 characters), `exit code N` or `ended by a signal` when stderr is empty, or `ambiguous device`. `profile_generation` starts at 0 and is bumped by every focused-app profile switch ([focused-app rules](masterhub-focus-rules.md#confirmation-is-tied-to-the-profile-shown)). `profile_id` and `profile_name` describe the profile of that generation: `profile_id` is `null` until a switch put a saved profile in place (the backend does not know the id of the profile a run started with), and `profile_name` is its name. The frontend resyncs its Resume dialog from them. A `session://state` event is sent whenever any field changes, including the countdown, and once as `running` right after a managed start.

## Safety rule

**Actions never resume executing on their own.** A session started with `execute: true` that is interrupted by sleep, unplugging, or a crash moves to `needs_confirmation` once its device is back. Only `resume_session(session_id, profile_generation)` restarts it, and the UI sends that command only after the user explicitly confirms. `profile_generation` names the profile the confirmation showed; if a profile switch replaced it in the meantime, the command is refused and the user is asked again. Time passing, inventory changes, and wake events cannot restart it. `resume_session` returns an error in any other phase. It restarts the session with its stored request (the original snapshot, or the saved profile a focused-app rule switched to) and its original `execute` value. Dry-run sessions (`execute: false`) restart automatically.

## Transitions

- **Sleep.** On suspend, the session stops the service through the existing SIGINT path, so the service restores hardware mode, as the official app does on suspend. The phase becomes `suspended`. After wake, the session waits `SETTLE_DELAY_MS` (2000 ms), then for the device identity to appear in the inventory. A dry run then restarts; an executing session moves to `needs_confirmation`. If a wake arrives before the pre-sleep stop has finished, the session waits for the old process to exit and then continues the same way.
- **Unplug, or a service exit the user did not request, with the device gone:** `waiting_for_device`. When the same identity reappears, a dry run restarts on the new path and an executing session moves to `needs_confirmation`. Removing the device from the inventory does not stop a running service by itself; the service exits when its reads fail. Rapid remove/add sequences cannot start a second process, because a restart happens only when no process exists.
- **Crash with the device present:** a bounded retry with backoff of 1 s, 2 s, 4 s, 8 s, 8 s (`MAX_ATTEMPTS` = 5). The next crash after that moves the session to `stopped` with reason `service_exited`. The attempt counter resets after a process has run for 30 s. For an executing session, every crash also moves it to `needs_confirmation`, and those crashes count toward the same limit. A start failure, such as a missing binary or the device being in use, counts as a crash. The app finds the binary through `OPEN_STREAM_HUB_SERVICE` or the bundled sidecar next to its executable; see [how the desktop app finds the binary](masterhub-service.md#how-the-desktop-app-finds-the-binary).
- **User stop.** `stop_session(session_id)`, or `stop_service` with either the session id or the current process id, ends the session from any phase, including `suspended`, `waiting_for_device`, and `needs_confirmation` where no process exists. Unknown ids are ignored. `stop_session` never stops a service that is not managed.
- **App exit.** All sessions end (`stopped`, reason `user`) before `Services::stop_all` stops the processes. Nothing is restarted.

## Power events

- **macOS (used):** native `NSWorkspaceWillSleepNotification` and `NSWorkspaceDidWakeNotification` observers, plus `NSWorkspaceScreensDidWakeNotification` as a backup wake source (see Missed wake), registered on the main thread at startup. The suspend handler waits up to `STOP_GRACE` + 1 s for the services to stop. Whether macOS actually delays sleep for that long has not been verified.
- **Ordering.** The driver handles queued sleep/wake events before any other queued input, so a sleep never waits behind queued work. Profile switches queued at the same time are handled together, and every process they interrupt is stopped in one parallel batch, as for sleep.
- **Starting while asleep.** Between a suspend and the next wake the driver spawns nothing, including a `start_service` that was queued behind the suspend. For an identified device it creates the session already `suspended` (reason `sleep`, no process); after wake and the settle delay it starts through the normal wake path, so a dry run starts and an executing session waits in `needs_confirmation`. An unidentified device cannot be managed, so its start is refused with `session::ASLEEP` ("the Mac is going to sleep; start the profile again after it wakes"). When that start is the one that cleared a missed wake (see below), it is refused with `session::JUST_WOKE` ("the Mac just woke; start the profile again in a moment") instead.
- **Missed wake.** Only a wake notification ends the asleep state. Background ticks and inventory changes never clear it, however much time has passed: the driver clock (`CLOCK_UPTIME_RAW` on macOS) stops during real sleep but runs during Power Nap dark wakes, macOS sends no sleep/wake notification for a dark wake, and the driver keeps ticking (at least once a minute) during one. The inventory watcher also keeps polling every second, but it sends an inventory only when the device list changes. A time-based valve in those paths could therefore restart dry runs while the Mac is asleep. The one exception is a user's Start: a start that arrives `MISSED_WAKE_MS` (10 minutes) of monotonic time after the suspend means the Mac is fully awake and its wake notification was lost, so it clears the asleep state through the normal wake path. Every session then waits the settle delay, a dry run starts, and an executing session waits in `needs_confirmation`. The started session waits the same way and spawns nothing at once. The ten minutes count **awake uptime**, not wall time, because the driver clock (`CLOCK_UPTIME_RAW`) stops during sleep. After a wake notification that really was lost, the user's Starts therefore stay deferred until ten minutes of uptime have passed since the suspend. Until then, an identified device gets a `suspended` session, an unidentified one is refused with `ASLEEP`, every session stays `suspended`, and a second Start on the same device is refused because the deferred session already runs it. The valve is checked before the Start is validated, so it fires even when that Start is then refused or invalid. Firing only clears the asleep flag and broadcasts `Resume`: the settle delay still applies, and executing sessions still wait for `resume_session`. Ten minutes is far beyond the pre-sleep stop (`SUSPEND_WAIT`, 10 s) and the roughly 30 s for which macOS lets an observer delay sleep, so a start queued behind a slow real sleep never trips it. The clock-gap detector is not added on macOS, because Power Nap dark wakes would trip it without a wake notification. Instead, `NSWorkspaceScreensDidWakeNotification` is a second source of `Resume`: the screens wake only on a full wake, never in a dark wake. It is forwarded only while a sleep notification has not yet been answered by a wake, so a display waking from display sleep alone restarts nothing. When `ScreensDidWake` already forwarded the `Resume` for a sleep, the `DidWake` that follows is not forwarded again, because a second `Resume` would restart the settle delay and could stop a process the first one had just started. A `DidWake` with no preceding sleep notification is still forwarded (`power::WakeGate`).
- **Known limitation (unverified).** A Start click that is dispatched only after sleep has begun could trip the valve during a later dark wake. For up to `SUSPEND_WAIT` the main thread is blocked in the `WillSleep` sink, so such a click can reach the driver after the suspend. If ten cumulative minutes of awake uptime have passed by then, for example across dark wakes, the valve fires while the Mac is still in a dark wake. It is also unverified that `NSWorkspaceScreensDidWakeNotification` never fires in a dark wake; check this with `pmset -g log`. No wall-clock gate for dark wakes has been added, and none of this has been tested on hardware.
- **Other platforms (fallback):** a clock-gap detector. Once per second it compares `Instant` (which does not advance during sleep on macOS or Linux) with `SystemTime`. If the wall clock moved at least 10 s further than the monotonic clock, the detector reports a wake. It can report only `Resume`, never a suspend beforehand, so the OS will already have interrupted the service without a clean hardware-mode restore. The session stops whatever is still running and restarts cleanly after the settle delay. A forward wall-clock jump of 10 s or more, for example an NTP correction, is also read as a wake. On Windows, it is not known whether `Instant` stops during sleep.

Dependencies: `block2`, `objc2-foundation`, and `objc2-app-kit` are now direct macOS-only dependencies. The same versions were already in `Cargo.lock` as Tauri dependencies, so nothing new is downloaded. The only newly enabled features are `NSOperation` on `objc2-foundation` and `NSWorkspace` on `objc2-app-kit`. `NSWorkspaceScreensDidWakeNotification` is part of the `NSWorkspace` feature, so it needs nothing new.

## Comparison with the official app (unverified)

Static analysis of MasterHUB 1.0.0.113 ([research notes](research/masterhub-1.0.0.113-static-analysis.md#startup-and-macos-transport-implications)) shows that on suspend the official app sets hardware mode. On resume, it waits 2 s, re-enters software mode, queries firmware, and requests a display refresh. OpenStreamHub does the following:

- It restores hardware mode by stopping the service, which already does that on SIGINT when it enabled software mode.
- It re-enters software mode by restarting the service with the same `--software-mode` flag.
- It does not query firmware or refresh the display; the service has neither feature.

The 2 s settle delay is copied from the official app and has not been checked against real hardware. None of the following has been checked on hardware either:

- How long a device takes to re-enumerate after wake.
- Whether paths or serial numbers stay stable.
- Whether a pre-sleep SIGINT finishes before the system sleeps.
