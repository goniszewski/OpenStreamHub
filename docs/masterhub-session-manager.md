# OpenStreamHub service session manager

The desktop app (`apps/open-stream-hub`) wraps every `masterhub-service run` that it starts in a **session**. A session keeps the run alive across system sleep, unplugging, and service crashes. The service has no reconnect logic of its own; see [masterhub-service](masterhub-service.md). The code is in `src-tauri/src/session.rs` (state machine and driver) and `src-tauri/src/power.rs` (sleep/wake events). A dry-run M131E replug recovered on a new path with the same serial on 8 October 2026; a repeat at `0a4162c` also retained the selected dial and recovered input. The user confirmed the app display returned after reconnect and the built-in animation returned after Stop for that repeat; sleep/wake and executing-session recovery have not been tested on hardware. See the [replug results](masterhub-hardware-results.md#desktop-app-dial-replug-m131e-8-october-2026). Automated tests use a fake clock, a fake service runner, a fake inventory, and fake power events.

## Identity and ids

- A session stores the original `start_service` request: profile snapshot, `execute`, and `software_mode`. Every restart reuses that request and changes only `path_hex`.
- The device is identified by **module + serial number**. HID paths can change after a replug or wake, so the session never relies on the path alone. To find a device again, the session needs an exact serial match. For a device whose serial is null or blank, it accepts a candidate only if exactly one device of that module is present. If several are present, the session keeps waiting with the detail `ambiguous device`. A different serial on the same port never counts as the same device.
- The session id is the first process's service id (`service:<path_hex>`) and does not change while the session lasts. When that id still names an older session that moved to another path, the new session is named `session:<uuid>` instead. `service_id` in the state event names the current process, which may have a different id after a replug, or is `null` when no process is running. `service://status` and `service://record` keep using the current process's id.
- `start_service` returns the **session id** for a managed run (including a start while asleep and a `session:<uuid>` name), or the service id of an unmanaged run. The frontend keys the run by that id as soon as the command resolves. Before that, a run that waits under its own key (`pending:service:<path>`, because a live session still carries that name) is matched to its first state event by the event's `service_id`, or, when the event has no process yet (a start while asleep), by the module and serial number the run was started on. The `start_service` reply can arrive before Tauri events that were sent earlier. If the reply names the path's own service id while the older run of that name has not yet reported `stopped`, the waiting run keeps its `pending:` key. The old session's remaining events, including its `stopped`, still update the old run, but none of them takes the path's `service://status` and `service://record` routing from the waiting run. The new process's status (`starting`, then `running`, which the backend reports inside `start_service`, before the session's first state event) and records therefore land in the waiting run. A waiting run stays eligible while its process has not ended (`starting`, `running`, or `stopping`). The new session's first event that is not `stopped` then adopts the waiting run, keeping its profile, profile generation, log, and counters, and replaces the old run. The same happens when that first event arrives before the reply: it is matched to the waiting run by its process id, or by module and serial number when it has no process. The old run never receives the new session or its process's status, the adopted run never takes the old run's profile or generation (so its Resume names the generation the new session reports), and a late `stopped` from the old session never ends the adopted run. The waiting run therefore leaves its `pending:` key once its session reports, and does not block later starts or stops on that path.
- Each session runs at most one process at a time. Two sessions can never share a device identity: `start_service` refuses a device that another session already owns. A serial-less device has no identity to compare, so a session without a process that waits for the same module, also without a serial (for example one started while asleep), claims every serial-less device of that module on any path, exactly as its reconnect picks the only device of that module. A second start is refused. A stopped session, or one whose process is still stopping, claims nothing.
- Every start runs the same request checks before a session exists, whether or not it spawns now: a valid profile, an execute mode the platform supports, and no process already running on that path (`Runner::check`, which uses `service::check_request`). An invalid profile started while asleep is therefore refused at once, not after wake.
- The Run panel retains its selected session by stable session id while the module is unplugged. Its waiting state, log and Stop stay visible alongside a disconnected device option; an unrelated module never replaces that selection just because it is first in inventory. A matching nonempty serial and module, or the session's current process path, follows the device to its new path. Serial-less sessions require one unambiguous module candidate without a current process path. Explicit choices remain authoritative, and Resume confirmations keep naming the captured session id. This UI behavior is regression-tested offline. The [real dial replug](masterhub-hardware-results.md#desktop-app-dial-replug-m131e-8-october-2026) exposed the earlier selection defect; a repeat at `0a4162c` showed Running with the dial still selected after reconnect and recovered rotation input. The user confirmed the app display returned after reconnect and the built-in animation returned after Stop. The intermediate disconnected UI was not inspected live; this accepts the recovered selection and dry-run reconnect on this dial, without establishing every intermediate state or other lifecycle behavior.
- When the app cannot identify the device from the latest inventory or from a fresh enumeration, it starts the service **unmanaged**, with `software_mode` cleared and no display settings or flags. Without a backend-known module identity, the frontend request cannot authorize a mode write. No session events are sent for that run.
- The app falls back to unmanaged runs only when no session driver was started. If the driver thread has died, `start_service` is refused with `session::DRIVER_STOPPED`, because an unmanaged run would ignore sleep. `stop_service` still stops the plain process in that case, since stopping never spawns anything. `stop_session` has no plain process to fall back to, so it returns `DRIVER_STOPPED` instead of silently doing nothing.

## Phases

| Phase | Meaning |
| --- | --- |
| `running` | The service process is running. |
| `suspended` | The system is asleep, or the 2 s settle delay after wake has not ended yet (`next_attempt_in_ms` shows the remaining time). |
| `waiting_for_device` | The device identity is not in the inventory, or the match is ambiguous. |
| `reconnecting` | A restart is in progress or scheduled (crash backoff, shown in `next_attempt_in_ms`). |
| `needs_confirmation` | The device is back, but the session executes actions, so it waits for the user. |
| `stopped` | Final. `reason` is `user` (stop or app exit), `service_exited` (too many crashes), or `start_refused` (the service refused to start; see Transitions). |

`reason` gives the most recent interruption: `sleep`, `device_removed`, `service_exited`, `start_refused`, `user`, `profile_switch` (a [focused-app rule](masterhub-focus-rules.md) replaced the profile), or `profile_action` (a [profile key](masterhub-actions.md#profile-nextprevious-profile) replaced it). It is `null` while the session is `running`. `detail` holds the last nonblank stderr line of a crashed or refused service (at most 512 characters), `exit code N` or `ended by a signal` when stderr is empty, or `ambiguous device`. The service's refusal of a schema-2 keypad profile without display sync is replaced by a sentence that names the Module control setting (`display::BUILT_IN_KEYPAD_REFUSAL`) rather than the service's flag. `profile_generation` starts at 0 and is bumped by every profile switch, from a focused-app rule or a profile key ([focused-app rules](masterhub-focus-rules.md#confirmation-is-tied-to-the-profile-shown)). `profile_id` and `profile_name` describe the profile of that generation: `profile_id` is `null` until a switch put a saved profile in place (the backend does not know the id of the profile a run started with), and `profile_name` is its name. The frontend resyncs its Resume dialog from them. A `session://state` event is sent whenever any field changes, including the countdown, and once as `running` right after a managed start.

## Safety rule

**Actions never resume executing on their own.** A session started with `execute: true` that is interrupted by sleep, unplugging, or a crash moves to `needs_confirmation` once its device is back. A profile key switch follows the same rule: it never confirms anything, and while a session waits for confirmation it has no process, so further profile keys do nothing. Only `resume_session(session_id, profile_generation)` restarts it, and the UI sends that command only after the user explicitly confirms. `profile_generation` names the profile the confirmation showed; if a profile switch replaced it in the meantime, the command is refused and the user is asked again. Time passing, inventory changes, and wake events cannot restart it. `resume_session` returns an error in any other phase. It restarts the session with its stored request (the original snapshot, or the copy of the saved profile that a focused-app rule or a [profile key](masterhub-actions.md#profile-nextprevious-profile) switched to, taken at the switch) and its original `execute` value. `session_profile(session_id, profile_generation)` returns that stored profile for the Resume dialog, and refuses a stale generation with `PROFILE_CHANGED`. Dry-run sessions (`execute: false`) restart automatically.

## Imported profiles (dry run only)

A profile imported from an official `.mhz` file ([importing MasterHUB profiles](importing-masterhub-profiles.md)) is dry-run only. The state lives in `<app data>/imported-profiles.json` (`src-tauri/src/import_flags.rs`), never inside the profile, and the backend is its only authority (the badge and the disabled Execute mode in the UI are convenience). Provenance is tracked two ways, so neither a new id nor a missing hint loses it:

- **Content hashes.** `content_hash` is the SHA-256 of the canonical profile JSON with its name emptied. A renamed copy, a re-imported JSON export, a save over another id, or the open draft of a deleted profile has the same hash and stays dry-run only. Hashes are never dropped when a profile is deleted.
- **Saved ids and lineage.** `save_profile` flags the saved id, and adds the new content's hash, whenever the content's hash is flagged or the target id or the draft's source id (`sourceProfileId`, the saved profile the draft was opened from, kept by the editor even after edits or deletion) is flagged. Records of deleted profiles are kept as tombstones.

`Runner::execution_guard` loads the flags once per check (once for a whole profile-key step) and checks in memory; the store is never read on the driver thread for this. It fails closed:

- **Start.** An executing Start is refused with `import_flags::DRY_RUN_ONLY`, before any session exists and also while asleep, when its `profile_id` or `source_profile_id` is flagged or its content hash is. This covers unsaved and edited drafts and the unmanaged fallback run. A dry run starts as usual.
- **Resume.** `resume_session` refuses an executing session whose held profile is flagged; it stays in `needs_confirmation`. An executing session restarts its process only through `resume_session` (after wake, reconnect or a crash it always waits for confirmation), so every restart with actions is checked again.
- **Focused-app switch.** `switch_session_profile` into a flagged profile from an executing session is refused, and the session keeps its process, profile and generation. A dry-run session may switch into it.
- **Profile key.** An executing session steps over flagged profiles when it resolves next or previous; with none left the request is dropped (`STEP_NO_TARGET`). A dry-run session steps into them.
- **Missing or damaged list.** The first import writes a sentinel (`profiles/.imported-profiles`). From then on a missing list, like an unreadable one, is an error: every Execute run is refused, every profile is listed as dry run only, and the listing carries `import_flags_error`. The sentinel also holds a redundant copy of every flagged hash (tombstones included). The only recovery is the explicit **Mark all profiles as needing review** action (`mark_all_profiles_for_review`), which flags every saved profile, restores the hashes from the sentinel and rewrites the list. Nothing advises deleting the file.
- **Exports and bounds.** `export_profile` takes `{ profile, sourceProfileId }`; when the source or the content is flagged, the exported content's hash is flagged and pinned before the file is written, so importing that file again stays dry run only (an unreadable list refuses the export). Saving a new version under a flagged id replaces that id's previous hash unless an export pinned it or another record names it. The list is compacted within 1,024 records and 4,096 hashes, but only tombstones (records of deleted profiles, oldest first) and hashes no live record names (unnamed first, then tombstoned, pinned exports last) are ever evicted; when that is not enough the write is refused, so the save, import or export fails closed. A previous version's hash is released only after the new version is on disk (a save whose folder flush fails after the rename counts as on disk), and never while any saved profile has that content, with or without a record. A profile with no binding has no hash flagged (it runs nothing and would match every blank profile); it stays tracked by its id and by drafts naming it as their source. A failed import keeps no record for a profile that never reached the disk; one that reached the disk although its write reported an error is rolled back with the rest of the import, or named in the error when it cannot be removed. A saved profile whose stored content is flagged counts as flagged by id too (for saves naming it as target or source, and for every Execute check), with or without a record. Every flag write lists the saved profiles (from the store's summary cache, which re-parses only changed files) and is refused when not every profile file can be listed; "Mark all profiles as needing review" refuses the same way, marks unreadable profiles by id, and refuses with a clear error when the marker cannot be read. A delete while the list is unreadable is refused when it cannot be remembered for recovery. Recovery restores the ids of dry-run-only records (deleted ones included) from the sentinel, plus ids deleted while the list was unreadable. While the list is unreadable, saves that name a target or source profile are refused (a brand-new profile with no source may still be saved; content matching a flagged hash is caught once the list is readable again). A refused save (a conflict) never flags its target. Residual risks are listed in [the user guide](importing-masterhub-profiles.md#residual-risks).
- **Allowing.** `allow_imported_profile_execution` takes `{ id, contentHash }`. Under the store lock the backend recomputes the hash of the saved file from what it parsed (never from the listing cache), refuses a mismatch (`CONFLICT_ERROR`), and clears the id's flag and that hash. An identical twin import keeps its own id flag but loses the shared hash. The backend cannot prove that a person clicked: the confirmation dialog, which names the profile and lists what it can do, is that step.

## Transitions

- **Sleep.** On suspend, the session stops the service through the existing SIGINT path, so the service restores hardware mode, as the official app does on suspend. The phase becomes `suspended`. After wake, the session waits `SETTLE_DELAY_MS` (2000 ms), then for the device identity to appear in the inventory. A dry run then restarts; an executing session moves to `needs_confirmation`. If a wake arrives before the pre-sleep stop has finished, the session waits for the old process to exit and then continues the same way. Countdown [timers](masterhub-actions.md#countdown-timer-timer) live only in the service process, so this stop cancels every running one (`timer_cancelled`, reason `stopped`) and none expires, notifies or plays a sound while the Mac is asleep. The restarted process after wake starts with no timers; they are not resumed. The same holds for every other stop or restart (unplug, crash, profile switch, user stop).
- **Unplug, or a service exit the user did not request, with the device gone:** `waiting_for_device`. When the same identity reappears, a dry run restarts on the new path and an executing session moves to `needs_confirmation`. Removing the device from the inventory does not stop a running service by itself; the service exits when its reads fail. Rapid remove/add sequences cannot start a second process, because a restart happens only when no process exists.
- **Setup refusal:** no retry. A process that exits with a nonzero exit code before it wrote its `service_start` record, while its device is still in the inventory, was refused during setup: an invalid or refused profile (such as a schema-2 keypad profile without display sync), a refused flag combination, stdout or stdin it cannot use, software mode on a module without it, a display sink that cannot be set up. The same arguments would be refused again, so the session moves straight to `stopped` with reason `start_refused` and the refusal in `detail`, shown once; an executing session stops too (nothing ran). The driver learns that a process started from its `service_start` record (`SpawnForwarder` sends `Input::Ready`, which marks only the current, running process); every restarted process must report it again. Some pre-start errors mean the module or the service's startup is not available *yet* rather than refused, and keep the crash backoff below (`session::TRANSIENT_ERRORS`): the path is not in the service's own inventory (`device path is not in the current inventory`, typically a module still enumerating after a replug or wake), HIDAPI could not open the device (`hidapi error: …`) or could not start (`Failed to initialize hidapi`), the action worker did not report ready in time (`action worker did not become ready`), or a record write such as `service_start` itself failed or timed out (`service log write failed`). A test pins each substring to the service's real text (`cooltek_sdk_cli` constants and the `hidapi` error display). Any other pre-start error, including a bare I/O error text, is treated as a refusal. An exit before `service_start` while the device is missing from the app's inventory is handled as an unplug, an exit by a signal (no exit code) or a spawn failure as a crash, both as before. The service writes `service_start` before it enters software mode, so a failure to enter software mode counts as a crash, not a refusal.
- **Crash with the device present:** a bounded retry with backoff of 1 s, 2 s, 4 s, 8 s, 8 s (`MAX_ATTEMPTS` = 5). The next crash after that moves the session to `stopped` with reason `service_exited`. The attempt counter resets after a process has run for 30 s. For an executing session, every crash also moves it to `needs_confirmation`, and those crashes count toward the same limit. A start failure, such as a missing binary or the device being in use, counts as a crash. The app finds the binary through `OPEN_STREAM_HUB_SERVICE` or the bundled sidecar next to its executable; see [how the desktop app finds the binary](masterhub-service.md#how-the-desktop-app-finds-the-binary).
- **Profile key.** A `profile` binding (next or previous) reaches the session as `profile_switch_requested` from a service started with `--profile-switch-requests`, which the app passes only when the running profile binds a `profile` action. The session picks the saved profile by name (case-insensitive, then exact name, then id) and wraps around at both ends; an unsaved draft goes to the first profile for next and the last for previous. Requests within 500 ms of an accepted one are dropped, as are requests while asleep or with fewer than two saved profiles. The switch follows the focused-app path: a dry run restarts at once, an executing session waits in `needs_confirmation` (reason `profile_action`).
- **User stop.** `stop_session(session_id)`, or `stop_service` with either the session id or the current process id, ends the session from any phase, including `suspended`, `waiting_for_device`, and `needs_confirmation` where no process exists. Unknown ids are ignored. `stop_session` never stops a service that is not managed.
- **App exit.** All sessions end (`stopped`, reason `user`) before `Services::stop_all` stops the processes. Nothing is restarted.

## Power events

- **macOS (used):** native `NSWorkspaceWillSleepNotification` and `NSWorkspaceDidWakeNotification` observers, plus `NSWorkspaceScreensDidWakeNotification` as a backup wake source (see Missed wake), registered on the main thread at startup. The suspend handler waits up to `STOP_GRACE` + 1 s for the services to stop. Whether macOS actually delays sleep for that long has not been verified.
- **Ordering.** The driver handles queued sleep/wake events before any other queued input, so a sleep never waits behind queued work. Profile switches queued at the same time are handled together, and every process they interrupt is stopped in one parallel batch, as for sleep.
- **Starting while asleep.** Between a suspend and the next wake the driver spawns nothing, including a `start_service` that was queued behind the suspend. For an identified device it creates the session already `suspended` (reason `sleep`, no process); after wake and the settle delay it starts through the normal wake path, so a dry run starts and an executing session waits in `needs_confirmation`. An unidentified device cannot be managed, so its start is refused with `session::ASLEEP` ("the Mac is going to sleep; start the profile again after it wakes"). When that start is the one that cleared a missed wake (see below), it is refused with `session::JUST_WOKE` ("the Mac just woke; start the profile again in a moment") instead.
- **Missed wake.** Only a wake notification ends the asleep state. Background ticks and inventory changes never clear it, however much time has passed: the driver clock (`CLOCK_UPTIME_RAW` on macOS) stops during real sleep but runs during Power Nap dark wakes, macOS sends no sleep/wake notification for a dark wake, and the driver keeps ticking (at least once a minute) during one. The inventory watcher also keeps polling every second, but it sends an inventory only when the device list changes. A time-based valve in those paths could therefore restart dry runs while the Mac is asleep. The one exception is a user's Start: a start that arrives `MISSED_WAKE_MS` (10 minutes) of monotonic time after the suspend means the Mac is fully awake and its wake notification was lost, so it clears the asleep state through the normal wake path. Every session then waits the settle delay, a dry run starts, and an executing session waits in `needs_confirmation`. The started session waits the same way and spawns nothing at once. The ten minutes count **awake uptime**, not wall time, because the driver clock (`CLOCK_UPTIME_RAW`) stops during sleep. After a wake notification that really was lost, the user's Starts therefore stay deferred until ten minutes of uptime have passed since the suspend. Until then, an identified device gets a `suspended` session, an unidentified one is refused with `ASLEEP`, every session stays `suspended`, and a second Start on the same device is refused because the deferred session already runs it. The valve is checked before the Start is validated, so it fires even when that Start is then refused or invalid. Firing only clears the asleep flag and broadcasts `Resume`: the settle delay still applies, and executing sessions still wait for `resume_session`. Ten minutes is far beyond the pre-sleep stop (`SUSPEND_WAIT`, 10 s) and the roughly 30 s for which macOS lets an observer delay sleep, so a start queued behind a slow real sleep never trips it. The clock-gap detector is not added on macOS, because Power Nap dark wakes would trip it without a wake notification. Instead, `NSWorkspaceScreensDidWakeNotification` is a second source of `Resume`: the screens wake only on a full wake, never in a dark wake. It is forwarded only while a sleep notification has not yet been answered by a wake, so a display waking from display sleep alone restarts nothing. When `ScreensDidWake` already forwarded the `Resume` for a sleep, the `DidWake` that follows is not forwarded again, because a second `Resume` would restart the settle delay and could stop a process the first one had just started. A `DidWake` with no preceding sleep notification is still forwarded (`power::WakeGate`).
- **Known limitation (unverified).** A Start click that is dispatched only after sleep has begun could trip the valve during a later dark wake. For up to `SUSPEND_WAIT` the main thread is blocked in the `WillSleep` sink, so such a click can reach the driver after the suspend. If ten cumulative minutes of awake uptime have passed by then, for example across dark wakes, the valve fires while the Mac is still in a dark wake. It is also unverified that `NSWorkspaceScreensDidWakeNotification` never fires in a dark wake; check this with `pmset -g log`. No wall-clock gate for dark wakes has been added, and none of this has been tested on hardware.
- **Other platforms (fallback):** a clock-gap detector. Once per second it compares `Instant` (which does not advance during sleep on macOS or Linux) with `SystemTime`. If the wall clock moved at least 10 s further than the monotonic clock, the detector reports a wake. It can report only `Resume`, never a suspend beforehand, so the OS will already have interrupted the service without a clean hardware-mode restore. The session stops whatever is still running and restarts cleanly after the settle delay. A forward wall-clock jump of 10 s or more, for example an NTP correction, is also read as a wake. On Windows, it is not known whether `Instant` stops during sleep.

Dependencies: `block2`, `objc2-foundation`, and `objc2-app-kit` are now direct macOS-only dependencies. The same versions were already in `Cargo.lock` as Tauri dependencies, so nothing new is downloaded. The only newly enabled features are `NSOperation` on `objc2-foundation` and `NSWorkspace` on `objc2-app-kit`. `NSWorkspaceScreensDidWakeNotification` is part of the `NSWorkspace` feature, so it needs nothing new.

## Module control

Settings has a **Module control** choice, **App** (the default) or **Built-in animation**, and a choice of what the dial screen shows (function name, the default; digital clock; analog clock; CPU usage on macOS; or nothing). Both are stored in `<app data>/display-settings.json` (`{"module_control":"app"|"built_in_animation","dial_content":…}`) with the same bounded, symlink-safe read and atomic owner-only (0600) write as `focus-rules.json` (`src-tauri/src/display.rs`). The commands are `display_settings` and `set_display_settings`.

- **Defaults and migration.** A missing file means App. The file written by the earlier experimental toggle (`{"enabled":…,"dial_content":…}`) is still read: `enabled: true` is App, an explicit `enabled: false` is Built-in animation, and the dial content is kept. Reading never rewrites the file; the next change in Settings writes the current shape. A damaged or unreadable file is reported in Settings (naming the file and saying to fix or delete it), never overwritten, and the Run panel keeps Run disabled with that error until the settings can be read (it also waits for the first read). A session the backend starts meanwhile uses an internal *unreadable* value (`ModuleControl::Unreadable`, never stored or sent): no module enters software mode, whatever the request says, nothing is drawn, and a schema-2 keypad profile is refused with a message that names the damaged file (`display::UNREADABLE_KEYPAD_REFUSAL`). `Runner::display_settings` defaults to that value too.
- **Read once per Start.** `Driver::start` reads the settings when the user starts a profile and keeps them, with the device's module, in the session's stored request (`StartRequest.display`, which the frontend cannot send: the field is skipped on deserialization and named fields are refused). Wake, reconnect, crash and profile-switch restarts reuse that copy. Changing the setting never stops, restarts or resumes anything; it applies at the next Start, and the Settings panel says so, including how many profiles keep their old value. An unidentified device (unmanaged run) runs without software mode or display flags, even if the request asks for software mode. This also keeps failed enumeration from bypassing unreadable settings.
- **App.** A Start on an M4315 or M131E always requests software mode (the session manager sets `software_mode` in the stored request, whatever the frontend sent; the frontend sends only what the user ticked), and `display::display_args` adds per spawn `--display-sync` for an M4315 running a schema-2 keypad profile and `--display-sync --dial-content <value>` for an M131E unless the dial content is off. A flat profile on the keypad runs in software mode without `--display-sync` (the service accepts the flag only with a schema-2 keypad profile). The flags follow the profile of each spawn, so a focused-app rule or profile key may switch a keypad session between flat and paged profiles. In the Run panel the software mode box is ticked, locked and explained for these two modules once the setting has loaded. Nothing is drawn on the keys of a flat profile's run.
- **Built-in animation.** No software mode is requested unless the user ticks the box in the Run panel, exactly as before this setting, and no display flags are passed. The service refuses a schema-2 profile on an M4315 without `--display-sync`, so the Run panel disables Run for it and `Driver::start` refuses it before anything spawns, both with a message that names the Module control setting. A focused-app rule or profile key that would switch a keypad session into such a profile is refused with the same message (`replace_profile`, like the dry-run-only guard), and the session keeps running its current profile.
- **Other modules.** Knobs, faders and the roller (M003K, M005S, M032LE) never get software mode or display flags: `Driver::start` clears `software_mode` for them whatever the request says, and the Run panel's box is off and locked for them.
- **Invariants.** Dry run stays the default, Execute still needs confirmation, nothing is spawned while asleep (a Start while asleep only snapshots the settings), executing sessions still wait in `needs_confirmation` after any interruption and resume with the value they started with, every spawn passes `--exit-on-stdin-eof`, and the app never writes firmware or draws on a module other than the M4315 and M131E. `display::spawn_args` keeps display flags to session-managed processes; an unidentified fallback never requests software mode. Nothing starts on connect.
- **Hardware status.** Software mode and display sync were run on one M4315 and one M131E ([hardware results](masterhub-hardware-results.md)). Key images are placeholders, only keys 0 to 2 were seen to agree between input and display, and display latency has not been timed.

## OBS WebSocket

Settings has an **OBS Studio** panel for `obs_scene` actions ([action catalogue](masterhub-actions.md#obs-scene-obs_scene)): a switch, off by default, a loopback host (127.0.0.1, ::1 or localhost) and a port, stored in `<app data>/obs-settings.json` with the display setting's bounded, symlink-safe read and atomic 0600 write (`src-tauri/src/obs.rs`), and a password field whose value is kept **in the app's memory only** (entered again after every app launch, never written to disk). The commands are `obs_settings`, `set_obs_settings` and `set_obs_password`; no reply ever carries the password.

- **Read once per Start.** `Driver::start` calls `Runner::obs_launch` when the user starts a profile and keeps the endpoint and a copy of the in-memory password in the session's stored request (`StartRequest.obs`, skipped on deserialization, so neither a profile nor the frontend can set it). Wake, reconnect, crash and profile-switch restarts reuse that copy: a profile switch never reads the setting again, and changing or clearing the setting or the password never stops or restarts a run. It applies at the next Start. Unlike the display setting it does not depend on the module, so a driver-started run on an unidentified device gets it too. A damaged settings file means off.
- **Per spawn.** `obs::obs_args` adds `--obs-endpoint <endpoint>` and, when a password was set, `--obs-password-stdin`; `Services::start_with_stdin` then writes the password line to the child's stdin pipe. OBS off: no OBS arguments, and every `obs_scene` press is logged as unavailable. Either way the child's stdin is a pipe the app keeps open until the child is reaped, and every spawn passes `--exit-on-stdin-eof`: if the app dies (crash or SIGKILL), the pipe closes and the service stops as on SIGTERM, restoring hardware mode ([service docs](masterhub-service.md#read-an-interface)). The process group, SIGINT on quit and restart behaviour are unchanged.
- **Residual risks.** Forgetting or changing the password, or turning OBS off, does not affect a running session: its snapshot is sent again on every respawn until the session is stopped. Plaintext copies of the password stay in the app's and each service's memory for their lifetime (nothing is zeroed), so a core dump would contain them. While OBS is not running, another local process can listen on the OBS port and collect a challenge answer to guess a weak password offline; use a long random OBS password. Details in the [action catalogue](masterhub-actions.md#the-obs-password).

## Comparison with the official app (unverified)

Static analysis of MasterHUB 1.0.0.113 ([research notes](research/masterhub-1.0.0.113-static-analysis.md#startup-and-macos-transport-implications)) shows that on suspend the official app sets hardware mode. On resume, it waits 2 s, re-enters software mode, queries firmware, and requests a display refresh. OpenStreamHub does the following:

- It restores hardware mode by stopping the service, which already does that on SIGINT when it enabled software mode.
- It re-enters software mode by restarting the service with the same `--software-mode` flag.
- It does not query firmware. It refreshes the displays only when the session started with Module control set to App: the restarted service then redraws keys or the dial from scratch.

The 2 s settle delay is copied from the official app and has not been checked against real hardware. None of the following has been checked on hardware either:

- How long a device takes to re-enumerate after wake.
- Whether paths or serial numbers stay stable.
- Whether a pre-sleep SIGINT finishes before the system sleeps.
